# development-automation Specification

## Purpose

Предоставляет разработчику единые команды запуска и проверки приложения, автоматическую проверку изменений в GitHub и регулярные предложения обновлений зависимостей.

## Requirements

### Requirement: Local development commands

Проект SHALL предоставлять из корня репозитория команды `task serve`, `task lint` и `task test` для запуска веб-сервера разработки, статического анализа и полного набора тестов соответственно. Команды SHALL работать при установленных Task и совместимом Flutter SDK без установленного RTK. Ошибка выполняемой команды SHALL приводить к ненулевому коду завершения задачи.

#### Scenario: Start the development server
- **WHEN** разработчик выполняет `task serve` при свободном порте 8080 и доступных зависимостях
- **THEN** приложение доступно по `http://localhost:8080`, браузер автоматически не открывается, а сервер работает до остановки разработчиком

#### Scenario: Run lint and tests without RTK
- **WHEN** разработчик запускает `task lint` и `task test` в окружении без RTK
- **THEN** команды запускают статический анализ и полный набор тестов, а при успешной проверке каждая завершается с кодом 0

#### Scenario: A local check fails
- **WHEN** анализатор или тесты завершаются с ошибкой
- **THEN** соответствующая задача возвращает ненулевой код завершения и показывает диагностический вывод

### Requirement: GitHub change checks

GitHub Actions SHALL автоматически проверять каждый push и pull request без фильтра по веткам или изменённым файлам. Проверка SHALL устанавливать зависимости и выполнять статический анализ и полный набор тестов, не требуя RTK или пользовательских секретов. Проверка SHALL иметь только разрешение `contents: read` и SHALL завершаться неуспешно при ошибке любого шага; запуск тестов после ошибки линтера не требуется.

#### Scenario: Check a push or pull request
- **WHEN** GitHub получает push или событие pull request, запускающее workflow
- **THEN** запускается проверка зависимостей, линтера и тестов; её результат отображается в GitHub Actions

#### Scenario: A check fails in CI
- **WHEN** установка зависимостей, линтер или тесты завершаются с ошибкой
- **THEN** проверка отмечается как неуспешная, а ошибка доступна в журнале соответствующего шага

### Requirement: Weekly dependency update proposals

Dependabot SHALL еженедельно проверять обновления зависимостей Pub в корне проекта и используемых GitHub Actions. При наличии подходящего обновления Dependabot SHALL предлагать его через pull request; конфигурация этого изменения SHALL NOT включать автоматическое слияние.

#### Scenario: A Dart package update is available
- **WHEN** еженедельная проверка Pub обнаруживает подходящее обновление зависимости проекта
- **THEN** Dependabot создаёт или обновляет pull request с изменениями соответствующих файлов зависимостей

#### Scenario: A GitHub Action update is available
- **WHEN** еженедельная проверка GitHub Actions обнаруживает подходящее обновление используемого action
- **THEN** Dependabot создаёт или обновляет pull request с изменением версии action в workflow

### Requirement: Безопасный деплой

Команда `task deploy` SHALL требовать явно заданный адрес назначения `TARGET`. Без него задача SHALL завершаться с ненулевым кодом и понятным сообщением до сборки и копирования файлов.

#### Scenario: Адрес назначения не задан
- **WHEN** разработчик выполняет `task deploy` без `TARGET` в окружении и `.env`
- **THEN** задача завершается ошибкой с указанием на отсутствующий `TARGET`, файлы не копируются

#### Scenario: Адрес назначения задан
- **WHEN** разработчик выполняет `task deploy` с заданным `TARGET`
- **THEN** приложение собирается и файлы сборки копируются по указанному адресу

### Requirement: Фиксированные версии сторонних инструментов в CI

Workflow GitHub Actions SHALL запускать сторонние инструменты из реестров пакетов только с фиксированной версией, а не с плавающей меткой вроде `latest`. Результат проверки SHALL оставаться в журнале шага и при неуспешном завершении.

#### Scenario: Запуск сканера интерфейса
- **WHEN** выполняется workflow `ui-craft-detect`
- **THEN** сканер запускается фиксированной версией, совпадающей с версией в заголовке workflow

#### Scenario: Скан нашёл ошибки
- **WHEN** полный скан при push завершается с ненулевым кодом
- **THEN** его JSON-вывод напечатан в журнале шага, а шаг завершается неуспешно
